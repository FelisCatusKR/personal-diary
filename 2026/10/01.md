## 오늘 배운 것

홈랩에 모니터링용 Raspberry Pi를 하나 더 들이면서, 호스트 이름을 어떻게 지을지 정리했다.

### RFC 1178 — 컴퓨터 이름 짓기

[RFC 1178](https://datatracker.ietf.org/doc/html/rfc1178) (1990)은 "모든 기기에 이름을 붙여라"가 아니라 **이름을 붙인다면 어떻게 고를지**에 대한 지침이다.

- 흔히 쓰는 말과 겹치는 이름을 피한다 (예: OS 이름 `openwrt`, 회사 이름 `oracle`)
- 그 기계만의 프로젝트·용도 이름을 피한다 → 용도가 바뀌면 이름이 거짓말을 한다
- 자기 이름을 쓰지 않는다
- 짧게, 철자 변형 없이, 숫자로 시작하지 않게, 영숫자만
- **실제 단어로 된 테마 이름**을 쓴다

### 홈랩에서 흔한 방식

| 방식 | 예 | 특징 |
|---|---|---|
| 순번 | `node01`, `pi-1`, `pi-2` | 가장 흔하다. 다만 Pi에서는 숫자가 모델 번호처럼 읽힌다 (`pi-3`이 Pi 3인가?) |
| 역할 + 순번 | `master-pi`, `worker-01`, `k3s-server01` | 클러스터처럼 역할이 고정일 때 맞는다 |
| 모델명 | `raspi4` | 기기가 적을 때 직관적. 같은 모델이 두 대가 되거나 교체하면 깨진다 |
| 테마 | 드라마 등장인물 등 | RFC 1178이 권하는 방식. 정보는 없지만 오해도 없다 |

참고: [glmdev — Building a Raspberry Pi Cluster](https://glmdev.medium.com/building-a-raspberry-pi-cluster-784f0df9afbd),
[pnavais/rpi4-ansible](https://github.com/pnavais/rpi4-ansible), [doemefu/homelab](https://github.com/doemefu/homelab),
[landsman/homelab #392](https://github.com/landsman/homelab/issues/392) (`nas` → `hank`로 테마 맞추기)

### 내 결론: 이름은 "네트워크에 보이는 기계 하나"를 가리킨다

- **역할은 이름에 담지 않는다.** 역할은 Ansible 인벤토리 그룹·네트워크 망·DNS 별칭(CNAME)이 나타낸다
  - 실제로 한 Pi가 "컨트롤 노드 + 앱 호스트"에서 "AI 에이전트 전용"으로 역할이 바뀐 적이 있다. 역할 이름이었다면 그때 이름을 바꿔야 했다
  - 서비스는 별칭으로 부른다 (예: `mon.lan` → 모니터링 기기). 기기를 바꾸면 별칭만 옮긴다
- 당장은 기존 순번 방식을 유지하고 "숫자는 도입 순서, 모델 번호가 아니다"를 문서에 적어 둔다. 이름을 바꾸면 인벤토리·DNS 고정 할당·`known_hosts`·문서를 전부 고쳐야 해서, 테마 이름은 기기가 늘어 한 번에 정리할 때로 미룬다

### 교체·재설치·듀얼부팅

기준은 **"교체 뒤에 옛 기계와 새 기계가 동시에 존재할 수 있는가"**이다.

| 상황 | 이름 |
|---|---|
| 같은 하드웨어에 OS 재설치 | 유지 (SSH 호스트 키만 재등록) |
| 디스크·SSD 교체 | 유지 (SMART 메트릭은 디스크 시리얼로 구분된다) |
| 데스크톱 메인보드·CPU 업그레이드 | 유지 (내장 NIC MAC이 바뀌니 DHCP 고정 할당 갱신) |
| Pi 교체 | 새 이름 — 보드가 곧 기계 전체라 옛 Pi가 온전히 남는다 |
| 새 기기를 들여 병행 운영 후 옛 기기 은퇴 | 새 이름, 역할(그룹·별칭)을 옮긴다 |

- 새 이름이 나은 이유
  - SSH 호스트 키가 어차피 바뀐다. 이름이 같으면 "호스트 키가 바뀌었다" 경고가 교체 때문인지 공격 때문인지 구분이 안 된다
  - 옛 기기와 새 기기를 동시에 켜 두는 병행 구축 → 커트오버가 가능하다
- **듀얼부팅은 하드웨어당 이름 하나.** NIC가 같으니 두 OS가 같은 MAC으로 DHCP를 요청하고, MAC 기준 고정 할당이면 같은 IP·이름을 받는다
  - **함정:** Windows는 MAC 기반 DHCP client-id를, Linux(systemd-networkd 등)는 기본으로 DUID 기반 client-id를 보낸다. dnsmasq가 "다른 client-id에 임대 중"이라며 고정 주소를 안 줄 수 있다 → Linux 쪽을 `ClientIdentifier=mac`(networkd) / `ipv4.dhcp-client-id=mac`(NetworkManager)로
  - SSH로 들어간다면 OS별 별칭 + `HostKeyAlias`로 호스트 키만 따로 저장한다

### 이름의 유니크 범위와 손님 Wi-Fi

- 공유기의 dnsmasq 하나가 여러 VLAN의 DHCP·DNS를 맡으면, 이름은 **VLAN이 아니라 공유기 전체(`.lan` 도메인)에서** 유니크해야 한다. 손님 Wi-Fi 기기가 DHCP로 보낸 이름도 같은 도메인에 등록된다
- dnsmasq 고정 할당(`dhcp-host`)으로 이름을 준 기기는 안전하다. 다른 기기가 같은 이름을 요청해도 내주지 않는다
- 동적 임대 기기는 이름을 빼앗길 수 있다. 손님 폰 이름이 우연히 `pikachu`면 `pikachu.lan`이 손님 기기로 풀린다 (방화벽이 손님 망을 막고 있다면 피해는 접속 실패 정도)
- 대응: 이름으로 접근하는 기기는 고정 할당. 손님 망은 `dhcp-ignore-names`로 이름 등록 자체를 안 하는 방법도 있다

### MAC 무작위화와 DHCP 호스트 이름

- 집 Wi-Fi는 **고정식(SSID별) 무작위 MAC**이면 충분하다. 공유기는 어차피 내 기기를 아는 쪽이라 순환식으로 숨길 이유가 없고, 고정식이면 DHCP 주소·이름이 안정적이다. 순환식은 공공 Wi-Fi에서 의미가 있다
- 기기 권한을 MAC이 아니라 망(어느 SSID에 붙었나)과 WireGuard 키로 정하면 MAC 무작위화와 충돌할 게 없다. 폰을 특정해야 하면 MAC 고정 할당보다 WG peer 주소가 낫다 (키에 묶여 있고 흉내 낼 수 없다)
- **함정:** 기기·OS 설정에 따라 DHCP 요청에 기기 이름이 실려 **공공 Wi-Fi에도 그대로 나간다.** "OO의 Galaxy" 같은 이름이면 MAC을 바꿔도 이름으로 식별된다 → 클라이언트 이름은 사람이 드러나지 않는 테마 이름이 낫다

### 테마를 쓸 때의 공통 원칙 — 이름에 의미를 싣지 않는다

어떤 테마를 고르든 지킨다.

> **테마 안의 분류(학교·동아리, 포켓몬 타입, 캐릭터 성격)는 기억을 돕는 장치일 뿐, 강제가 아니다.**
> 테마를 쓰는 원래 목적은 RFC 1178대로 **이름이 역할을 담지 않게** 하는 것이다. 분류는 기기를 처음 들일 때 이름을 고르는 실마리로만 쓴다.
> 나중에 역할이 바뀌어도 이름은 그대로 둔다. 예를 들어 VPN·방화벽 게이트웨이를 새로 들여 공유기가 AP로 물러나도 공유기 이름은 그대로다.
> "에이전트 호스트니까 이 동아리여야 한다"처럼 분류를 역할로 다루기 시작하면, 피하려던 역할 이름으로 돌아간다.

- **분류 기준은 바뀌지 않는 하드웨어 속성이다.** 서버, 네트워크 장비, 거치형 컴퓨터(서버 목적 아님), 휴대 기기(노트북·폰·태블릿), 가전.
  "관리할 수 있는 기기"처럼 권한으로 나누면 권한이 바뀔 때마다 분류가 흔들린다
- **권한은 이름이 아니라 키와 네트워크 경로에 있다.**
  - 관리 주체는 컨트롤 키(가능하면 하드웨어 키)를 가진 곳이다. 지금은 집 데스크톱의 컨트롤 노드 VM 하나
  - 휴대 기기는 잃어버릴 수 있으니 노트북도 폰과 같은 입장이다. 원격 관리는 VPN으로 집 데스크톱에 붙어서 한다. 공유기 관리 화면은 VPN에서 직접 열리지 않게 막아 둔다
  - 나중에 노트북에 관리 권한을 주더라도 바뀌는 건 키와 방화벽 규칙뿐이고, 이름은 그대로다

### 테마 아이디어 (모집 중)

기기 종류별로 테마를 나누면 풀 크기와 성격을 맞출 수 있다.

**상시 인프라 → 페르소나 5 괴도단 코드네임** (열 개 남짓이라 오래 쓰는 기기에 아껴 쓴다)

| 코드네임 | 어울리는 기기 |
|---|---|
| `joker` | 데스크톱 (컨트롤 노드 VM이 돌고 지시를 내리는 자리) |
| `queen` | 서비스 호스트 (규칙대로 실무를 굴리는 학생회장) |
| `crow` | AI 에이전트 호스트 (팀에 있지만 끝까지 믿지 않고 격리해 둔다) |
| `navi` | 모니터링 (뒤에서 전체를 지켜보는 내비게이터) — 영문판 `oracle`은 회사 이름과 겹쳐서 일본판 이름으로 |
| `mona` | 공유기 (모두를 태우고 다니는 몬나 버스) |
| 남은 이름 | `skull`, `panther`, `fox`, `noir`, `violet` |

**개인 클라이언트·IoT → 포켓몬** (1,000개가 넘어 자주 바뀌는 기기에 맞다. 대부분 만든 말이라 겹침이 적다. `ditto`처럼 일반 단어인 것과 `Mr. Mime`처럼 기호가 들어간 것은 피한다)

| 기기 | 타입 | 예 |
|---|---|---|
| 폰·태블릿 | 비행·페어리 | `pidgey`, `togepi`, `sylveon` |
| 노트북 | 에스퍼 | `abra`, `espeon`, `alakazam` |
| 스위치·AP | 전기·강철 | `magnemite`, `jolteon`, `klink` |
| IoT 가전 | 로토무 | 폼이 세탁기·전자레인지·냉장고·선풍기·잔디깎이라 가전에 딱이다 |

- IoT는 기기가 보내는 이름을 못 바꾸는 경우가 많다 → dnsmasq 고정 할당(MAC 기준)으로 덮어쓴다. IoT는 무작위 MAC을 거의 안 써서 통한다

**후보 2: 블루 아카이브 하나로** — 학생이 200명 안팎이라 풀이 크고, 학교·동아리가 이미 분류 역할을 한다

규칙: **분류 = 학교, 시리즈 = 동아리.** 모자라면 같은 동아리 → 같은 학교의 다른 동아리 → 아직 아무 분류도 안 쓰는 다른 학교 순으로 넓힌다.
학교 단위로 경계를 두면 한 분류가 커져도 다른 분류의 이름을 침범하지 않는다.

| 분류 | 학교 | 시리즈 |
|---|---|---|
| 거치형 컴퓨터 (서버 목적 아님) | (학교 밖, 선생님 쪽) | `sensei` → `arona`, `plana` → `shittim`, `shaked` |
| 서버 | 밀레니엄 | 서비스 호스트는 세미나(`yuuka` → `noa`, `koyuki`), AI 에이전트 호스트는 게임개발부(`aris` → `momoi`), 모니터링은 베리타스(`kotama` → `hare`, `chihiro`), 확장은 엔지니어부(`utaha`, `hibiki`, `kotori`) |
| 네트워크 장비 | 아비도스 | 대책위원회 — 공유기 `ayane`(오퍼레이터), VPN·방화벽 게이트웨이 `hoshino`(방패 들고 앞에서 막는다), 이후 스위치·AP `shiroko`, `nonomi`, `serika` |
| 개인 클라이언트 | 트리니티 | 동아리별 |
| IoT 가전 | 게헨나 | 급식부(`fuuka`, `juri`)부터 |

- 학교·동아리는 위 "공통 원칙"대로 기억용이다. 게이트웨이(`hoshino`)를 들여 공유기가 AP로 물러나도 공유기는 계속 `ayane`다
- 로마자 표기는 **글로벌판 공식 영문 표기로 통일**한다 (`yuuka`/`yuka`, `aris`/`alice` 같은 변형 방지 — RFC 1178 "철자 변형 피하기")
- 일반 단어와 겹치는 이름(`midori`, `yuzu`, `mika` 등)은 건너뛴다
- 이름은 하드웨어를 따른다. 데스크톱을 새로 사면 새 기기는 `sensei`를 물려받지 않고 같은 분류의 다음 이름(`arona`)을 받는다
- 동아리 멤버 구성은 이름을 붙일 때 공식 자료로 한 번 확인한다
