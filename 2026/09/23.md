## 오늘 배운 것

홈랩에서 AI 코딩 에이전트를 돌리는 머신을 정리하면서, 에이전트 격리와 키·인증 관리를 같이 설계했다.

### AI 에이전트는 호스트가 아니라 격리된 환경에서

- 에이전트를 호스트 유저로 돌리면 그 유저가 가진 모든 것(docker 그룹 = root 등가, SSH 키, 시크릿 복호화 키)에 에이전트가 닿는다
- Docker 앱 컨테이너보다 **Incus 시스템 컨테이너**가 에이전트용으로 잘 맞는다
  - systemd·apt가 있는 전체 OS라서 에이전트가 필요한 도구를 그 자리에서 설치할 수 있다
  - 스냅샷 → 망가지면 즉시 롤백
  - `limits.memory`, `limits.cpu`로 호스트 보호
  - 작업물은 별도 custom volume에 두고 컨테이너는 언제든 재생성 가능하게
- 함정들
  - Raspberry Pi 커널은 기본값이 `cgroup_disable=memory` → 메모리 제한이 조용히 무시된다. `cgroup_enable=memory` 필요
  - Docker가 iptables `FORWARD`를 DROP으로 바꿔서 Incus 브리지 트래픽이 막힌다 → `DOCKER-USER`에 허용 규칙
  - `incus-admin` 그룹도 docker 그룹처럼 root 등가다
- 에이전트는 인프라 레포에 **PR까지만**. apply는 사람이 한다. GitOps로 main이 곧 프로덕션이면 브랜치 보호는 필수

### VPN 역할 나누기

- 안드로이드는 VPN을 **하나만** 켤 수 있다. 이미 WireGuard로 집 공유기의 광고차단 DNS를 강제하고 있다면, 그 WG 망에 에이전트 컨테이너를 peer로 붙이는 게 가장 매끄럽다
  - 폰은 VPN을 바꿀 필요 없이 그대로 에이전트 UI에 접속
  - 서비스는 WG 인터페이스에만 바인딩 → LAN에 포트를 열지 않아도 된다
  - 허브(공유기)에서 방향별로 허용 범위를 좁힌다
- SSH를 Cloudflare Tunnel로 하고 있다면 Tailscale의 남은 가치는 "장애 영역이 다른 비상 접속 경로" 하나뿐이다. 쓰지 않으면 키 만료로 비상시에 못 쓰게 되니, 유지한다면 주기적으로 확인해야 한다

### Windows 게이밍 데스크톱을 Ansible 제어 노드로

- Ansible은 Windows 네이티브 제어 노드를 지원하지 않는다
- WSL2/Hyper-V를 켜면 Windows 자체가 하이퍼바이저 위 root partition으로 내려간다 → 게임 성능 이슈
- 하이퍼바이저 없이 VirtualBox/VMware로 작은 Linux VM을 필요할 때만 켜면 된다
- **함정: Hyper-V 기능만 끈다고 끝이 아니다.** 메모리 무결성(HVCI), Credential Guard, Virtual Machine Platform, Windows Sandbox 등도 하이퍼바이저를 켠다. 켜진 채로 VirtualBox를 쓰면 조용히 Hyper-V 위에서(WHP) 돈다
  - `systeminfo` 하단이 "Hyper-V 요구 사항"이면 꺼짐, "하이퍼바이저가 검색되었습니다"면 켜짐

### SOPS + age 키 관리

- 같은 키를 여러 곳에 복사하는 백업보다 **수신자를 여러 명** 두는 게 낫다. SOPS는 data key를 수신자마다 따로 암호화하므로 아무 키 하나로도 복호화된다
  - 평소 쓰는 키 + **종이에만 존재하는 복구 키**
  - 복구 키는 `age-keygen`을 `-o` 없이 실행해 화면에서 종이로 옮긴다. SSD에는 쓰지 않는다
- 키가 유출되면 수신자 교체만으로는 부족하다. git 히스토리의 옛 암호문은 옛 키로 영원히 풀린다 → `sops rotate` + **시크릿 값 자체를 재발급**
- 백업은 대체 불가능한 키에 집중. SSH 키처럼 재발급 가능한 건 백업하지 않아도 된다
- sops는 `SOPS_AGE_KEY_CMD`를 지원해서 키를 환경변수로 export하지 않고 명령 출력으로 넘길 수 있다. age 플러그인 신원(`AGE-PLUGIN-…`)도 지원
- 복구 연습은 반기마다: 종이에서 공개키를 다시 계산해 일치 확인 + 실제 복호화까지

### YubiKey 5 vs Security Key

| 기능 | Security Key | YubiKey 5 |
|---|---|---|
| FIDO2/WebAuthn/패스키, SSH `ed25519-sk` | ✅ | ✅ |
| PIV (→ `age-plugin-yubikey`) | ❌ | ✅ |
| OATH TOTP 저장 | ❌ | ✅ |
| OpenPGP, OTP, challenge-response | ❌ | ✅ |

- SSH와 웹 2FA만 쓸 거면 Security Key로 충분
- SSH FIDO 키(`ed25519-sk`)는 age 신원으로 쓸 수 없다. age를 하드웨어에 넣으려면 PIV
- 펌웨어는 업그레이드가 안 되므로 5.7+ (패스키 100개). 폰에서 쓰려면 NFC 모델
- 분실 대비로 두 개를 사서 모든 곳에 둘 다 등록

### PIV냐 암호화 파일이냐

- **PIV도 실행 중 메모리에 풀린 평문 시크릿은 못 지킨다.** 지켜주는 건 "키 자체와 앞으로의 시크릿"이다

| | PIV | 암호화 파일 |
|---|---|---|
| 제어 노드가 뚫리면 공격자가 얻는 것 | 터치하는 동안 복호화된 시크릿 | 키 자체 (파일 + 키로거로 잡은 passphrase) |
| 유효 기간 | 공격자가 머무는 동안 | 영구 (git 히스토리까지) |
| 사고 대응 | 노출된 시크릿만 교체 | 키 교체 + rotate + 전체 시크릿 교체 |

- 키를 Bitwarden에 넣는 건 기각: 비밀번호 관리자 백업을 age로 암호화하면 순환 의존이 생기고, 볼트 하나가 뚫릴 때 인프라 시크릿까지 같이 넘어간다
- 판단 기준: "뚫렸을 때 모든 시크릿을 재발급하는 수고를 감수할 수 있는가"

### 웹 2FA를 비밀번호 관리자에 맡기기

- 맡기면 그 계정의 보안 = 볼트의 보안. 잠금 해제된 볼트가 있는 PC가 뚫리면 비밀번호와 2FA가 한꺼번에 넘어간다
- TOTP보다 패스키가 낫다 (도메인에 묶여 피싱 방어)
- **등급을 나눈다**
  - 최상위(비밀번호 관리자 자체, 이메일, 코드 호스팅, DNS/CDN, 비밀번호 관리자를 호스팅하는 클라우드, 도메인 등록기관) → 하드웨어 키 WebAuthn
  - 나머지 → 비밀번호 관리자의 패스키/TOTP
- 이렇게 하면 하드웨어 키 등록처가 몇 곳으로 고정되어 예비 키를 꺼낼 일이 드물다
- 셀프호스팅 비밀번호 관리자는 웹 볼트 대신 **네이티브 클라이언트**를 쓴다. 배포 파이프라인이 뚫리면 서버가 내려주는 웹 볼트 JS가 바뀌어 마스터 비밀번호를 가로챌 수 있다

### 비밀의 위치: 시크릿마다 저장소 하나

| 종류 | 위치 |
|---|---|
| 기계가 쓰는 시크릿 | SOPS(git)에만 |
| 사람이 입력하는 비밀 | 비밀번호 관리자 |
| 마스터 비밀번호, PIN | 기억 |
| age 복구 키, 2FA 복구 코드, PUK | 종이 |

- 하드웨어 키를 둘 다 잃어도 종이 + 기억만으로 전부 복구되어야 한다

### 결론

- 장기적으로 **YubiKey 5 두 개 + PIV로 age 키**를 하드웨어에 넣는다
  - 시크릿이 늘어날수록 "노출된 것만 교체"의 이점이 커진다
  - 키 사본 관리가 필요 없고 제어 노드 이동도 쉽다
- 순서는 구매와 무관한 것부터: **비밀번호 관리자 백업 → 종이 복구 키 + 복구 연습 → 에이전트 격리**
